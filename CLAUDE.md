# RoleCall — Build Instructions

RoleCall is a job-application tracker. This file governs how the app is built so it stays visually and structurally consistent. See `../rolecall_plan.md` for product context (why, user stories, features).

## Design system — follow it strictly
The design system lives in `design-system/`. Before building or restyling any UI, read `design-system/design-system.md`. The visual target is `design-handoff/today.html` (open it in a browser) — **a frozen reference, not code: never import its `tokens.css` or copy its markup.**

- **Import `design-system/tokens.css` once, globally.** Reference its CSS variables for every color, font, spacing, radius, shadow, and z-index.
- **Never hardcode** a hex color, font size, spacing value, or radius. If a value you need isn't a token, add it to `tokens.css` first, then use it.
- **`tokens.css` has two layers, and components may only use the semantic one.** The raw palette (`--navy-*`, `--coral-*`, `--crimson-*`) exists to define the semantic layer (`--color-*`, `--sidebar-*`); a component referencing `--navy-200` directly is a bug even though it renders fine today. This split is what keeps a dark theme a token addition rather than a rewrite.
- **Spacing is the 4pt scale only** (`--space-*`). No arbitrary pixel values.
- **Text color** uses `--color-text` / `--color-text-heading` / `--color-text-secondary` / `--color-text-muted` (the floor for text). `--color-text-placeholder` is placeholders only; `--color-text-disabled` is non-text. **The sidebar is a dark ground with its own `--sidebar-*` text ramp** — never mix the two.
- **Three typefaces, one job each:** Playfair Display (`--font-display`) for page titles and the wordmark only · Public Sans (`--font-sans`) for all UI · Roboto (`--font-task`) for task titles only. Use the `--text-*` role tokens, not ad-hoc font shorthands.
- **Coral comes in three strengths for accessibility — don't collapse them.** `--color-accent` / `--focus-ring` / `--color-title-accent` (brand `#e5482b`) are for non-text marks and the 30px title accent only; buttons fill `--color-primary`, links use `--color-link`. Brand coral fails AA as body text or behind white text. **Danger is crimson (`--color-danger`), never coral.**
- **Radius:** `--radius-sm` checkboxes/inputs/menu items · `--radius-md` nav items, search, cards, menus · `--radius-lg` task tiles, dialogs · **`--radius-full` for buttons, chips, status and priority pills, dots and avatars** — pills are the control shape (this reversed the Aug 2026 "no pill buttons" rule).
- **Reuse components** before building new ones — especially `Button.tsx`; don't re-declare button CSS in a screen's module.
- **Tasks are floating tiles; every other collection is flat rows.** A task is a white `--radius-lg` tile with `--shadow-task`, 3px (`--task-gap`) between tiles — on Today and on job detail alike (one `TaskRow`). Notes, questions, contacts, writing rows stay flat: divider + hover fill, no border/radius/shadow, 44px floor. Cards are for genuinely discrete floating items, never for page layout.
- **Priority is a rank, not a status.** Use the `--priority-*` navy tokens — never a pipeline color. Status colors belong to `statuses.json` and nothing else.

## Status / pipeline
- `design-system/statuses.json` is the **single source of truth** for pipeline status. It drives kanban columns, status badges, filters, and the database status enum.
- Store a job's status as its `id` in a **database ENUM column** whose allowed values are exactly the `id`s in `statuses.json`. Use `label` for display only; resolve `label`/`dot`/`badgeBg`/`badgeFg` in the UI from this file — never store them or re-pick status colors inline. Changing the pipeline means editing `statuses.json` **and** running an enum migration.
- Changing the pipeline = editing that one file.
- `design-system/task-statuses.json` (in progress / waiting / to do) and `design-system/priorities.json` (high / med / low) are the equivalent sources of truth for tasks. Same rule: DB enum of exactly those `id`s, edit-the-file-then-migrate. **The list order is Today's group order and nothing else** — In progress, Waiting, then To do: finish what you started, chase what is blocked, and the queue is the only group you can ignore today. Because order is presentation, the status a new task is born in is stated separately as **`$default`** in the same file, read by both `design_system.TASK_STATUS_DEFAULT` (the model default) and `defaultTaskStatusId`; re-ordering the groups must never quietly change what a new task is. Task **completion is a separate boolean**, not a status. Task status carries **no color** — colour on a task row belongs to the job's pipeline stage.

## Icons
- Use **Phosphor** (`@phosphor-icons/react`) per `design-system/icons.md`. **Never use emoji as icons.**
- Icon-only buttons need an `aria-label`; decorative icons are `aria-hidden`.

## Accessibility (non-negotiable)
- Keep the global `:focus-visible` ring on every interactive control — don't strip outlines.
- **44×44px is the floor on touch.** Controls with a transparent hit-area wrapper (checkbox, kebab, priority tag) stay 44px at every size. Buttons and menu items size from `--control-height` (36px on a fine pointer), which rises to 44px automatically under `@media (pointer: coarse)` — the one relaxation, and only where a mouse is driving.
- Native form elements (`<input>`, `<select>`, `<button>`) with associated labels.
- Design responsive — users are often on a phone. Two breakpoints carry the app: **900px** (sidebar → drawer) and **600px** (row/band reflow).
- Wrap animation in `@media (prefers-reduced-motion: reduce)`.

## Conventions
- **Comment every functional unit.** In all code files, put a concise comment above each function, component, class, or self-contained block explaining what it does, so the code reads top-to-bottom without deciphering it. Say what and why, not a restatement of the syntax; keep it to a line or two.
- Nav vocabulary: **Today · Jobs · Writing Library** — match routes to these labels. The old export's Board/Table/Archive/Contacts wording is superseded; don't reintroduce it.
- **Closed jobs are a filter under Jobs**, not a top-level destination — there is no Archive nav item. Writing Library is a different thing entirely: the reusable pool of cover letters, blurbs and impact statements (see story 3 in `../rolecall_plan.md`).
- When a change lands, keep this file and `design-system/` as the source of truth — fold new decisions back in rather than letting components drift.

## Stack & architecture (settled)
- **Frontend:** Vite + React + TypeScript in `frontend/` (strict tsconfig: `verbatimModuleSyntax`, `erasableSyntaxOnly`, no unused locals — use `import type`, no enums). Styling is **CSS Modules over `tokens.css`**; there is no component library.
- **Backend:** Django 6 + Django REST Framework in `backend/` (project `config`, app `tracker`), SQLite (`backend/db.sqlite3`, gitignored). API under `/api/` (`jobs`, `tasks`, `notes`, `questions`, `contacts`, `writing`, `meta`).
- **Python** lives in the repo-root **`.venv/`** (Python 3.14, machine-wide install). Always use `.venv/Scripts/python.exe`; the bare `python` command is a Windows Store stub and won't work.
- **Enums are generated from the JSON, never hardcoded.** `backend/tracker/design_system.py` loads `design-system/*.json` to build model `choices` **and** DB `CheckConstraint`s. Editing a JSON file changes the constraint → `makemigrations` produces the migration. This is the enforcement mechanism behind the "edit the file, then migrate" rule.
- **Frontend resolvers** in `frontend/src/design-system/*.ts` import the same JSON so labels/colours resolve from one source of truth. Vite `server.fs.allow` includes the repo root so the frontend can import `../../design-system/`.

## Data model (see `backend/tracker/models.py`)
- **Job** (role, company [default "undisclosed"], applied_on, posting_url, status, fit_score, created_at). **`fit_score`** (0–10 to one decimal, null = unrated) is a column of its own rather than a line inside a note, so jobs can be ranked by it later without parsing "~8.5/10" out of prose; a DB check constraint backs the range. The **reasoning** behind a score is a note like any other judgement — `description_summary` and `fit_notes` were added and then removed (migrations `0002`/`0003`) once the job page proved notes already carry that. A separate **job priority** is still owed (stories 4–6) and overlaps `fit_score` — settle whether they are one field before adding it. · **Task** (job FK `SET_NULL`, title, category, status, is_done, priority, due_on, created_at) · **Note**/**Question** (attached to exactly one of a job or task) · **Contact** (M2M → jobs) · **WritingPiece** (job FK `SET_NULL`, type, title, body [markdown], `derived_from` FK to self, created_at, **updated_at** — the only `auto_now` in the app) / **WritingPassage** (piece FK `CASCADE`, text, position, use_count, last_used_at).
- **Task job/category is "never both"** (not "exactly one"): a task may briefly have neither after its job is deleted (`SET_NULL`). Completion is the `is_done` boolean, never a status.
- **Auth is deferred:** no `user` FK yet; adding it later is an additive migration. DRF runs open (no auth class, `AllowAny`) for the single-user MVP — lock down when auth lands.

## App shell (built)
- **Left sidebar** (`components/Sidebar.tsx`, 240px, the dark `--sidebar-bg` navy rail with its own `--sidebar-*` text ramp): Playfair wordmark · nav (Today · Jobs · Writing Library; active item is a pale pill at weight 800) · a `Pipeline` section of active stages with live counts linking to `/jobs?status=<id>` · account slot. Collapses to an overlay drawer below 900px.
- **`components/AppShell.tsx`** owns the frame and mounts `useTracker()` — one fetch feeds both the sidebar counts and the Today list. Screens render into its `Outlet` and read data via `useTrackerContext()`.
- **`components/Toolbar.tsx`** is the sticky per-screen header and **owns the page title** — screens don't render their own `<h1>`. An optional `accent` prop sets one word of the title in italic `--color-title-accent`. The title ellipsises; the actions never shrink (a right-aligned row that shrinks overflows over the title). **Below 600px** the actions wrap to their own row and the bar stops being sticky — two rows are too tall to pin over a phone — so Today's sticky group headers re-anchor to `top: 0` there.
- **New application is an app-level action, not a Jobs one.** The shell owns the `JobForm` dialog and hands screens `onNewApplication()` on the context alongside `onOpenNav()`, so the same dialog opens from any toolbar. Saving navigates to `/jobs?status=<id>` — the board is the only place the job is visible — replacing the history entry when already on Jobs and pushing from anywhere else, so Back returns you to where you were.
- **Routes:** `/` Today · `/jobs` · `/jobs/:id` · `/writing` · `/writing/:id` (react-router).

## Today screen (built)
- Page title **"Step *forward*"** (Playfair, coral italic accent word). Pipeline band directly on the page ground (no container) over the grouped task list. Rows render **checkbox · title · chip · priority · row menu** as a **floating task tile** (`--shadow-task`, `--radius-lg`, 3px apart; done tiles trade the lift for `--shadow-done`) — no dates (`due_on` is stored but not displayed), no waiting day-count. **Every task title uses `--color-text`** — done and job-less tasks are not differentiated by text colour. Done tasks strike through in place (chips mute) and **keep their position** — checking a row off never makes it move. The row menu (kebab) holds **Edit** — which opens the task dialog on that row, the one place every field of a task is edited — and **Delete task**. There is no inline rename: a row-local editor that reaches one field of six is a second, weaker form. Delete is behind the menu (no separate confirm dialog yet).
- Groups by task-status order under an eyebrow header carrying a count; sorts by **priority rank alone**. **A row moves between statuses by dragging it into another group** (same optimistic PATCH + snap-back as the Jobs board, and the same deferred `dragstart` so Chrome doesn't cancel the drag). Empty groups are hidden at rest but **all appear while a drag is in flight** — a group you can't see is a group you can't drop into, and moving the last task out of a status would otherwise strand it. Drag is never the only route: the menu's **Edit** opens the dialog with its Status select, which is the keyboard and touch path to the same change. Completion is deliberately not a sort key: a row that jumps the moment you check it pulls itself out from under the cursor. The sort is stable, so tasks at equal rank hold the API's newest-first order.
- **`TaskForm` both creates and edits** (`components/TaskForm.tsx`, composed from `Dialog.tsx` + `Form.module.css`) — same fields, same rules, only the verb differs, exactly as `JobForm` does for jobs. It covers every field a task has: title · job · category · status · priority · due date. **`is_done` appears only when editing** — a task you're creating isn't done, so there is nothing to switch; an existing one has a state worth correcting from here as well as from the row's checkbox. The list header button, the empty-state CTA and a row menu's **Edit** all open it, and it is **mounted only while open** so a new task starts empty and an edit starts from the row it was opened on.
  - **Job and category are mutually exclusive** in the form as in the model: picking a job disables the category select and clears it, so "never both" can't be violated from the UI. Blank due date sends `null`.
  - Saving POSTs and prepends the row. Create is **not optimistic** — the row needs the server's id, and the chip needs the company/stage the server resolves from the FK — so the dialog stays open on failure with the typing intact. **An edit is awaited too, for the same reason**: the saved record is merged back whole (`onUpdateTask`), because re-pointing a task at another job changes the `job_company`/`job_status` chip that the patch itself never mentions. The row's own edits — checkbox, priority pill, a drag between groups — stay optimistic with revert-on-failure, since they have nowhere to show a failure.
- **A `Show completed` toggle** (`components/Toggle.tsx`) in the list header hides done tasks from every group; groups that empty out drop away, and the header only offers the toggle once something is actually done. It **persists across sessions** via `usePersistedBoolean` (`localStorage`, `rolecall.` prefix, every access guarded because blocked storage throws rather than returning null) — how the list should read is a standing preference, not something to re-decide every visit. It stays a view preference, not a database column.
- Two empty states, with different words: nothing tracked yet (invites the first task) and everything done with the completed rows hidden (points back at the toggle).
- Loading renders skeleton rows; the error state is a card with a working **Try again** wired to `reload()`.

## Jobs screen (built)
- **A kanban board** (`components/JobBoard.tsx` + `JobCard.tsx`): one column per **active** stage in `statuses.json`, all five on screen at once. **No horizontal scroll ever** — columns are `flex: 1 1 0` and share the pane; `--board-column-min` is only the wrap floor. Columns are `--color-bg-sunken` wells so the white cards read forward.
- Cards carry **role · company · status chip · applied date**. **The whole card opens `/jobs/:id`**, via a link stretched across it (`::after { inset: 0 }`) rather than a click handler, so middle-click and copy-link still work; the **role is its own link to `posting_url`** and the status pill sits above that layer, so both stay clickable. The card is still the drag handle, and a click synthesised at the end of a drag is swallowed. The date renders only when set, as short month + day (`Mar 12`).
- **`?status=<id>` focuses a column** (accent ring), it does not filter to one — hiding the other stages would defeat the board. Both the sidebar Pipeline links and the pipeline band land here.
- **New application** (`components/JobForm.tsx`, composed from `Dialog.tsx` + `Form.module.css`) covers every field a job is born with: role · company · stage · applied date · posting link. The toolbar button, the empty-state CTA and Today's toolbar all open the shell's one dialog; it is **mounted only while open** so each visit starts empty.
  - **Stage offers active stages only** and defaults to the focused column, else the pipeline's first stage — creating straight into a closed stage would save a job with nowhere to appear. Blank **company omits the field** so the model's `undisclosed` default applies (an empty string is a 400). A posting link with no scheme gains `https://` on blur; **applied date is capped at today**.
  - Saving POSTs, adds the card, then focuses the column it landed in via `?status=`. Create is **not optimistic** — the card needs the server's id — so the dialog stays open on failure with the typing intact.
- **Closed stages have no column and no surface yet** — a closed-jobs filter is still owed.
- Wraps below 900px, stacks below 600px. Loading uses `SkeletonBoard`; the error state and `.srOnly` compose from `routes/Pane.module.css` rather than being restated.

## Job detail screen (built)
- **`/jobs/:id` is the per-job workspace** (`routes/JobDetail.tsx`): where one application stands and what's outstanding on it. Today is the cross-job "what do I do now"; this page is "what's the state of this one". Reached by clicking a card on the board; the Toolbar carries a back affordance (`backTo`), the **role as the page title**, and **Edit details** in its actions slot (the writing drawer's trigger joins it there later).
- **The page is split by KIND of information, and that split is the design.** A **main column** holds the work you act on; a **sticky rail** (`--detail-rail-width`) holds reference you only read. Its first version was one column of four identical-looking sections and read as scattered — the fix was structural, not cosmetic.
- **Hierarchy is carried by three header sizes**: 30px Playfair Toolbar title (role) · 16px `--text-section` main sections · 12px `--text-eyebrow` rail blocks. Rail blocks sit on `--color-bg-sunken` (the board-well surface) — **not cards**, which are never page layout. Tasks here are the same floating tiles as Today; notes and questions stay flat rows.
- **Order is header → Tasks → Notes → Questions**, then the rail. Tasks are what you act on; the log has the traffic once a job is live, and a question is usually raised by something just logged. **No count badges anywhere** — section headers are labels, not a dashboard.
- **Each list keeps a distinct left gutter**, which is what lets the eye tell them apart at a glance: tasks = 44px checkbox · notes = date column · questions = a `?` / `✓` mark in the same column.
- **Header** (`components/JobHeader.tsx`) is now just **company + inline `StatusPill`** — the two facts worth reading first. Stage is the page's most frequent edit by a distance, so it stays inline.
- **Rail — `JobFacts.tsx`**: a real `<dl>` of Applied (**or "Not applied yet"**, a real state) · Added · Fit (**or "Not rated"**) · Posting, the row omitted when there's no URL.
- **Rail — `ContactList.tsx`**: avatar + name + what they are, the row itself opening the editor. **`ContactForm.tsx`** creates someone new *or links a person who already exists on another job* — one person, several applications. **Every contact write sends the COMPLETE `jobs` list**: the M2M is declared on `Contact`, so it's only writable from that side and the API *replaces* the list — a partial one silently detaches them from their other jobs. **Removing** unlinks from this job; if it was their last, the contact is deleted, since an unlinked person has no surface anywhere. Note the model has **no per-job role** — "Recruiter" describes the person, not the person on this job.
- **Adding is a button, not a live field.** Each section's header carries **+ Add**; `InlineAdd.tsx` opens under it for notes and questions, and tasks open the shared **`TaskForm`** dialog with `initialJobId` set. The composer stays open after a save (clears and refocuses) so several notes can be logged in a row; Escape or Cancel closes it.
- **Tasks reuse `TaskRow`** — never a second task row — with **`showChip={false}`**, since every row here belongs to the job in the title. The tile is a flex row, so an absent chip leaves no gap — the same reason the 600px breakpoint can simply hide it. Rows read from the **shell's** task store, so Today, the sidebar and this list share one set of rows.
- **Notes edit in place.** A pencil sits beside the delete (both revealed on hover or focus), opening the entry in a field shaped like the composer that wrote it: Escape abandons, ⌘/Ctrl+Enter saves, and saving an unchanged note skips the PATCH. Awaited rather than optimistic, so a failure keeps the editor open with the typing intact. **The date stays `created_at`** — editing corrects the record of what happened, it doesn't re-file the entry under today. There is no `updated_at`, so an edit leaves no trace; add the column if that ever matters.
- **Questions:** open first, resolved folded behind **Show resolved**. **Answering *is* resolving** — `answer` and `resolved_at` are one PATCH, so a question can't sit answered-but-open. Reopening clears the stamp and keeps the answer.
- **State split:** `useJobDetail(id)` owns the detail payload (fit, contacts, notes, questions) and PATCHes what only this page can see; the **shell owns the board-visible fields** (role, company, stage, dates) so the board and sidebar counts follow, and the page mirrors the **saved** record back into its copy (the API normalises — a cleared company returns as `undisclosed`).
- `GET /api/jobs/:id/` **embeds contacts, notes and questions** so the page loads in one request; the board's list payload stays slim. A **404 is its own state** ("No such application"), separate from the server-unreachable error.
- **Below 900px** the rail stacks under the main column. DOM order is main→rail at every width, so tab order always matches reading order.
- **Still owed here:** the **writing drawer** (needs `writing_piece`), and a **confirm step for deleting** a note or question (they delete optimistically, matching tasks).

## Writing Library (built)
- **`/writing` is the reusable pool** of resumes, cover letters, blurbs and impact statements (story 3). Two screens: the index, and `/writing/:id` for one piece.
- **Read and copy only.** Nothing here creates, edits or deletes a piece — the API is a `ReadOnlyModelViewSet` and says so. **Writing is authored on a job page** (still to build), which is what keeps the library *a view over the data* rather than a second place to remember to populate. Until that lands, content arrives via `seed_writing` or the Django admin.
- **Copy is the primary action, not open.** Every unit of reuse carries `CopyButton`: each passage row, each search hit, and the whole body. A successful clipboard write increments `use_count` and stamps `last_used_at` — which is how **"best writing" is computed rather than starred**. `Copy all` deliberately increments nothing: crediting every passage for one bulk copy would inflate the signal "most used" depends on.
- **Two result modes on one screen, switched by the query.** No query lists **pieces** (title · type tag · company · date); a query lists **passages** (highlighted excerpt · source piece + company · use count). **Filters narrow documents, search returns lines** — type/company/sort stay applied in both, and are applied server-side so the two modes narrow by identical rules.
- **Passages are derived, never authored.** `passages.py` splits `body` on blank lines and list items (headings dropped) and `WritingPiece.save()` re-derives on every save — **the only `save()` override in the app**, so the admin and the seed command chunk identically. It **preserves `use_count` by matching text**: unchanged passages keep their row and their counts; a reworded one starts again. `body` being real markdown is load-bearing — one unstructured blob becomes one useless passage and topic search quietly stops working.
- **Search is SQLite FTS5** (`search.py` + migration `0006`, the only hand-written SQL in the repo): an external-content virtual table over `writing_passage`, kept in sync by DB triggers so every write path — ORM, admin, bulk delete — indexes for free. `porter` tokenizer, so "fundraiser" finds "fundraising". `snippet()` returns the excerpt.
- **Raw input must never reach FTS5.** `team's`, `donor OR` and `"unclosed` are each a syntax error and would be a 500. `to_match_query()` reduces the input to quoted word runs with a `*` on the last (so it narrows as you type). The cost: **boolean operators are treated as literal words**, which is right for a search box.
- **Excerpt highlighting uses control-character sentinels** (STX/ETX from `chr(2)`/`String.fromCharCode(2)`), not brackets or markup, so a passage containing `[` or `<b>` can't corrupt it and `Excerpt.tsx` renders `<mark>` by splitting text nodes — nothing is ever interpreted as HTML.
- **Search results are capped at 50** rather than paginated: no other endpoint in this API has an envelope, and search shouldn't be the one that does.
- Filters live in the URL (`?q=&type=&company=&sort=`) like the board's `?status=`; the query is **debounced 200ms** (`useDebounced`, the first in the app) because this is the first screen whose narrowing is a server round-trip.
- State is in route-local hooks (`useWritingLibrary`, `useWritingPiece`), not the shell: nothing outside `/writing` reads pieces, and the piece page needs a **`missing`** state the shell's `LoadState` doesn't have.
- **The index's empty state carries no CTA** — a deliberate exception to the design system's rule, because there is genuinely no next step in-app until job-page authoring exists, and a button that opens nothing is worse than none.
- **Still owed:** authoring on the job page (and with it the pull drawer), plus `Duplicate & tailor` — `derived_from` is populated and displayed both ways, but nothing forks a piece yet.

## Running the app
- **Seed** (real data, gitignored): `.venv/Scripts/python.exe backend/manage.py seed_local` (reads `seed.local.json`; wipe-and-reload).
- **Seed writing** (separate on purpose): `.venv/Scripts/python.exe backend/manage.py seed_writing` (reads `writing.seed.local.json`; wipe-and-reload **within the writing tables only** — it never touches jobs, tasks, notes, questions or contacts). Pieces name their job by **company + role together**, since company alone is ambiguous; a miss leaves the piece unattached and warns rather than failing the load. Passages are not in the file — they are derived from `body`. See `writing.seed.local.example.json` for the shape.
- **Backend:** `.venv/Scripts/python.exe backend/manage.py runserver 8000`
- **Frontend:** `cd frontend && npm run dev` (serves `:5173`, calls the API at `localhost:8000`).
- **npm needs the system CA:** this machine intercepts TLS, so npm install/create must run with `NODE_OPTIONS=--use-system-ca` (don't disable strict-ssl). Not needed once deps are installed.
